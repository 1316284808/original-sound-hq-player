# AudioPlayer 内存开销与分配分析 — 2026-09-27

当前实现的主要增量是无缝预载的第二套会话，以及改变倍速时重建会话产生的临时大数组。此次固定负载短测没有发现持续增长的托管对象保留；不能由此排除实际曲目、原生解码器、设备驱动或长时间播放的泄漏。

## 测量条件与边界

- 代码基线 `9159d0f6`，加本次 0.25–5× 固定档位变更；Windows x64、.NET 11 RC、NativeAOT、真实 WASAPI 共享输出，Latency=300 ms，音量为零。
- WAV、双声道、48 kHz；高采样率另测 192 kHz。正常组播放 12 秒，各组使用新进程；倍速反复切换组执行 60 次 1× / 1.5× 切换。未开启响度扫描、卷积或 EQ。
- baseline 表示没有排队预载下一曲；gapless 唯一增加下一曲预载，未到自然换曲点。实际主程序会在播放开始后规划下一曲，因此默认启用无缝且队列有下一曲时，会长时间持有两个会话。
- 进程计数由外部客户端读取。托管计数由独立诊断入口每秒采样；生产代码、编译方式和 GC 延迟模式保持相同，发布版没有加入采样或强制 GC。
- 末尾发送 `MusicEnd`、等待两秒，再做测试专用完整 GC，用来识别可回收垃圾。`MusicEnd` 的实际语义是停止并 seek 到开头，保留当前 Session 和输出以供重播，并不释放整台引擎。
- 表格是单次对照矩阵，并非多次统计实验。绝对 Working Set 受页面驻留影响；不能把不同进程的细小差异解释为功能成本。

## 进程实测

单位 MiB（1024² 字节）。Private / Working Set 是第 5 秒起至播放段结束的样本均值；分配速率使用约 3–11 秒区间，包含 IPC、线程任务及采样器。

| 场景 | Private | Working Set | 托管分配 KiB/s | 停止并诊断 GC 后的堆 |
|---|---:|---:|---:|---:|
| 48 kHz，单会话 1× | 7.79 | 18.41 | 15.96 | 1.12 |
| 48 kHz，增加无缝预载 | 10.45 | 20.64 | 15.82 | 1.11 |
| 48 kHz，压限开启 | 8.06 | 18.41 | 16.05 | 1.11 |
| 48 kHz，0.25× | 9.50 | 19.47 | 15.92 | 1.42 |
| 48 kHz，5× | 9.78 | 19.53 | 15.93 | 1.46 |
| 48 kHz，反复切换倍速 | 13.47 | 23.62 | 1130.04 | 1.12 |
| 192 kHz，单会话 1× | 11.39 | 20.93 | 16.06 | 3.09 |
| 192 kHz，增加无缝预载 | 17.64 | 27.51 | 15.95 | 3.10 |

无缝预载增加约 2.66 MiB / 6.25 MiB 私有内存（48 / 192 kHz）。取消预载后，经诊断 GC，托管堆回到对应单会话水平。没有看到本场景中的第二套会话持续保留。

60 次倍速切换共分配约 68.11 MiB，私有内存峰值 14.96 MiB，自然 Gen2 计数增加 18；停止后完整 GC 的堆为 1.12 MiB。最后一次自然 GC 的 committed 约 4.89 MiB，其中碎片约 3.18 MiB。这支持“反复重建带来临时分配和堆碎片/保留”的解释，不支持将累计分配量当成常驻内存。

稳定播放各组约 16 KiB/s，开启倍速、预载或压限都没有令该速率明显上升。停止后仍有类似分配，说明不能全部归因于音频 DSP。源码中 IPC 发布每 50 ms 唤醒，客户端存活检查每 100 ms 创建可取消的 `Task.Delay`；这是值得进一步做分配栈验证的路径，本次未将总速率精确归属到它们。

## 缓冲与生命周期

1. **无缝预载不是只读几帧。** `PlaybackEngine.Gapless.cs:103` 调用完整 `Session.Open`，创建解码器、环形缓冲、scratch、DSP 状态和解码线程。环满后解码线程等待，持有这些资源到切换或取消。已完成/失败的相同预载请求有去重，未发现每秒重复打开同一文件的路径。
2. **PCM 环随采样率与声道数增长。** `Session.cs:246` 容量是两倍设备延迟，限制在 0.5–2 秒。300 ms 设置下，每会话环为 `sampleRate × 0.6 × channels × 8` 字节：48 kHz 双声道 450 KiB；192 kHz 双声道 1800 KiB。再加每会话解码 scratch 256 KiB，以及 FFmpeg 原生上下文、线程和小型 DSP 状态。下一曲没有自己的输出设备；同一输出负责拼接。
3. **倍速缓冲固定，不随歌曲时长增长。** `TempoProcessor.cs:25` 按 hop、搜索窗口、倍速和声道数预分配三组数组。48 kHz 双声道构造实测：0.25× 323,752 B，1.5× 331,432 B，5× 354,472 B；1× 不创建处理器。此处包含对象/数组头，不含 Session 其他缓冲。
4. **倍速改变目前重建整个输出会话。** `PlaybackEngine.cs:972` 检测 rateChanged，进入 `ChangingSetting`，重建解码器、PCM 环、scratch 和 WASAPI 输出 scratch。原数组解除引用后由 GC 回收，因此只看任务管理器可能观察到阶梯式增长。固定档位避免连续数值输入产生大量不同配置，但不消除每次有效切换的重建成本。
5. **压限器没有大数组。** `DynamicsProcessor` 只持有少量系数和历史标量；默认旁路、启用后逐块处理已有样本。它不是本次 MiB 级增量的主要来源。
6. **卷积可进一步放大预载成本。** 独立构造实验：双声道 8192 taps 的系数准备分配约 514 KiB，每个滤波器历史/工作区再分配约 541 KiB；1024 taps 对应约 65 / 89 KiB。准备分配包含临时工作，不能直接当作存活量。文件 IR 不缓存，下一首会再次准备；曲线缓存最多四套，历史仍按滤波器独立。相同卷积跨曲连续时保留旧渲染历史，并同时有新目标滤波器，因此峰值可能超过简单的双份估算。未在本次进程矩阵开启卷积。

`--measure-playback-memory` 对真实 FFmpeg 解码和 WSOLA 处理预热后测量当前线程分配：

| 路径 | 本次样本 | 托管分配 |
|---|---:|---:|
| 原速解码 | 144,000 帧 | 0 B |
| 0.25× 解码/伸缩 | 576,000 帧 | 0 B |
| 1.5× 解码/伸缩 | 96,000 帧 | 0 B |
| 5× 解码/伸缩 | 28,800 帧 | 0 B |
| 压限处理 | 10,000 块，每块 1024 帧 | 0 B |

这是 JIT 下的方法级、当前线程托管计数实验；不是“整个播放器零分配”，不覆盖原生 FFmpeg 分配或所有媒体格式。没有采集完整分配栈、堆转储或 suspend/restart 事件，因此不报告 STW 时长或类型热点排名。

GC 的 `SustainedLowLatency` 模式可以以更大的堆换取较少的前台 Gen2 回收，但仍会发生回收；项目采用此模式不能解释为禁止 GC。[微软延迟模式说明](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/latency)。`GetTotalMemory(false)` 与进程 Working Set、Private Bytes、最近一次 GC 的 committed 是不同指标；首次 GC 前 committed 返回 0 不代表没有堆。[微软 GC 性能说明](https://learn.microsoft.com/en-us/dotnet/standard/garbage-collection/performance)。

## 建议顺序

- 若主要问题是正常播放时常驻内存上升，优先评估**临近曲尾才预载**或更小的预载缓存。需要按原曲剩余时间和倍速计算窗口，并留足解码/磁盘余量；过迟预载会降低无缝成功率。当前关闭无缝或只有一首可播放曲目可作为对照。
- 若主要问题是反复调速后内存上涨，优先研究**保留设备输出、只重建/重置必要的伸缩与解码状态**。需验证原曲时间映射、排空、暂停、seek 和取消竞态。不能仅改一个 rate 字段。
- 大缓冲复用应限定格式和生命周期并设容量上限；直接套用全局 ArrayPool 可能保留高水位，未必降低工作集。不要因观察到 GC 后内存不马上下降而加入周期性 `GC.Collect()`。
- 后台约 16 KiB/s 属于次要目标。可进一步对 IPC 唤醒、可取消等待及计时任务做栈级采样；避免为了少量分配引入复杂的取消与退出逻辑。

本轮只增加隔离采样工具与分析，未为内存问题改变发布版 GC、缓存或预载策略。尚未覆盖用户实际曲目、FLAC/DSD/网络、ASIO/独占、多声道、响度冷扫描、真实卷积链及长时间自然连续切歌。工具与复现命令见 [MemoryProbe](../_tools/AudioPlayerMemoryProbe/README.md)，完整数值见 [CSV](../_tools/AudioPlayerMemoryProbe/Results-2026-09-27.csv)。
